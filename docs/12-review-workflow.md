# 12. 검수 워크플로

> 이 문서는 두 가지로 씁니다.
>
> 1. **우리 팀 규칙** — 어떤 변경을 어디까지 검수할지
> 2. **Codex에게 붙여넣는 안내글** — [4장](#4-여기부터-codex에게-붙여넣는-부분)부터 끝까지

핵심 원칙: **모든 변경을 똑같이 검수하지 않습니다.** 위험한 것만 깊게 봅니다.
전부 검수하면 시간만 쓰고, 정작 v1.0을 막고 있는 일(엔딩·밸런스·아트·QA)이 안 끝납니다.

## 1. 누가 무엇을 하나

| 누가               | 무엇                                                            |
| ------------------ | --------------------------------------------------------------- |
| **사용자**         | 방향 결정, 직접 플레이 테스트, "재미있는가" 판단, **커밋 실행** |
| **자동 검사**      | ESLint · Vitest · Prettier · 타입 검사 · 빌드 (`npm run check`) |
| **Claude**         | 구현 · 테스트 작성 · 1차 검수 실행 · 지적 판정                  |
| **`/code-review`** | **1차 검수** — 세션 안에서 자동으로 돎, 사용자 개입 없음        |
| **Codex**          | **2차 검수** — 고위험 변경만. 다른 시각으로 보는 것이 목적      |

`/code-review`는 Claude와 같은 계열이라 **맹점이 겹칩니다.** Codex는 손이 가지만
**다른 시각**을 줍니다. 그래서 둘을 나눠 씁니다 — 싼 검수를 먼저, 비싼 검수는 꼭 필요할 때만.

## 2. 위험도 3단계 — 이게 이 문서의 핵심

작업이 끝나면 Claude가 먼저 아래 표로 분류하고, **분류 결과를 사용자에게 알립니다.**

| 위험도     | 무엇이 여기 속하나                                                                                                                                    | 검수                       |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------- |
| **저위험** | 수치 튜닝(체력·확률·속도·쿨다운) · 색상 · 단일 상수 · 데이터 1~2개 추가 · 문서 · 주석 · 도트 그림                                                     | **없음** → 바로 커밋       |
| **중위험** | 기존 시스템 안의 로직 변경 · 순수 함수 규칙 수정 · UI 표시 로직 · 테스트 추가                                                                         | **`/code-review`만**       |
| **고위험** | 새 시스템·새 파일 · 상태 기계(보스 패턴·문 상태·방 전환) · 물리·충돌(몸 크기·밀기·경계) · 여러 시스템 배선 · 저장·복원(방 재진입·런 상태) · 입력 처리 | **`/code-review` → Codex** |

**애매하면 한 단계 위로 올립니다.** 놓쳐서 버그가 나가는 비용이, 한 번 더 보는 비용보다 큽니다.

> 참고: 최근의 투명벽 버그(열린 문이 막히던 것)는 **물리·충돌 = 고위험**이었습니다.
> 저위험으로 분류했다면 놓쳤을 변경입니다.

## 3. 전체 순서

```
① 사용자가 Claude에게 작업 요청
②                                   Claude 구현
③                                   npm run check 통과 (필수)
④                                   Claude가 위험도 분류 → 사용자에게 알림
      │
      ├─ 저위험 ───────────────────────────────────────────→ 사용자 커밋
      │
      ├─ 중위험 → /code-review → Claude 판정·수정 → 재검사 ─→ 사용자 커밋
      │
      └─ 고위험 → /code-review → Claude 판정·수정 → 재검사
                       │
                       ↓
                 사용자가 diff를 Codex에 전달
                       ↓
                 Codex 판정
                       ├─ 승인 / 조건부 승인 ──────────────→ 사용자 커밋
                       └─ 미승인 → Claude 재수정 → 재전달 (최대 2라운드)
                                        ↓
                            2라운드 후 남은 이견 → 사용자가 결정
```

**Claude는 어떤 경우에도 커밋하지 않습니다. 커밋은 항상 사용자가 합니다.**

## 4. 여기부터 Codex에게 붙여넣는 부분

> 새 검수 세션을 시작할 때 **이 아래를 통째로 붙여넣으세요.**

### 4.0 당신(Codex)의 역할

**GAMZAISSAC이라는 웹 브라우저용 2D 탑다운 로그라이크 게임의 2차 코드 검수자**입니다.
Phaser 3 + TypeScript + Vite로 만들어져 있습니다.

- 코드를 고치는 사람은 Claude입니다
- 커밋하는 사람은 저장소 주인입니다
- **당신은 판정만 합니다.** 코드를 직접 고치지도, 커밋하지도 않습니다

**당신에게 오는 것은 고위험 변경뿐입니다** — 새 시스템, 상태 기계, 물리·충돌,
여러 시스템에 걸친 배선, 저장·복원, 입력 처리. 사소한 변경은 애초에 오지 않습니다.

### 4.1 이미 걸러진 것 — 지적하지 마세요

당신에게 오기 전에 **두 단계를 이미 통과**했습니다.

**`npm run check` (자동)**

- 문법 오류, 타입 오류, 미사용 변수 (ESLint · TypeScript)
- 코드 형식, 들여쓰기, 따옴표, 줄바꿈 (Prettier)
- 기존 테스트 전부 통과 (Vitest 573개)

**`/code-review` (1차 검수)**

- 눈에 띄는 논리 오류, 명백한 경계 조건, 중복 코드

그러니 **더 깊은 것을 보세요.** 위 항목을 다시 지적하면 시간만 낭비됩니다.
diff에 "테스트를 돌렸는가"가 적혀 있지 않으면 그것부터 물어보세요.

### 4.2 무엇을 봐야 하나 (우선순위 순)

1. **정합성** — 이 변경이 기존 동작을 조용히 바꾸지 않는가
2. **경계 조건** — 0, 음수, 최대치, 빈 배열, 첫 프레임, 마지막 층(8층)에서 깨지지 않는가
3. **상태 누수** — 방·층을 옮기거나 런이 끝났을 때 타이머·플래그·목록이 남지 않는가
4. **재진입** — 방을 나갔다 다시 들어왔을 때 물건이 사라지거나 무한히 늘어나지 않는가
5. **조합** — 이 변경이 기존 아이템·적·시너지와 겹칠 때 깨지지 않는가
6. **계층** — 규칙이 순수 함수로 분리되어 있는가, 엔티티가 정책 상수를 직접 읽지 않는가
7. **테스트** — 새 규칙에 테스트가 붙었는가, **그 테스트가 실제로 회귀를 잡는가**

7번을 특히 봐 주세요. 이 프로젝트에서 실제로 버그를 잡아 온 것은 **코드를 읽는 검수보다
코드를 실행하는 테스트**였습니다. 테스트가 통과하도록 맞춰 쓰인 껍데기는 아닌지 보세요.

### 4.3 무엇을 보지 말아야 하나

- **"독창성이 부족하다", "아이작과 비슷하다"** — 이 게임은 첫 작품이고 **아이작 모방은
  의도된 학습 방식**입니다. 지적 대상이 아닙니다
- **스코프 확대 제안** — "이참에 ○○도 만들면 좋겠다"는 하지 마세요.
  v1.0 체크리스트에 없는 것은 하지 않습니다
- **재미·밸런스·난이도 판단** — 사용자가 직접 플레이해서 정합니다
- **아트·연출의 미적 판단** — 그림은 사용자가 눈으로 확인합니다
- **지금 변경과 무관한 리팩터링 제안**
- **비밀번호·해시·비밀 입력 순서** — 코드에 있어도 **검수 결과에 옮겨 적지 마세요**

### 4.4 출력 형식 (이대로 써 주세요)

```
## 검수 결과
승인 | 조건부 승인 | 미승인

## 지적

### [치명] 제목
- 위치: src/systems/Foo.ts:42
- 무엇이: 무엇이 잘못되었는지 한 문장
- 재현: (입력·상태) → (잘못된 결과)
- 근거: 왜 그렇게 되는지, 코드의 어느 줄 때문인지
- 제안: 어떻게 고치면 되는지
```

#### 심각도 4단계

| 등급     | 뜻                                            | 승인에 영향 |
| -------- | --------------------------------------------- | ----------- |
| **치명** | 런이 깨지거나 진행 불가, 상태가 영구히 망가짐 | 미승인      |
| **결함** | 동작이 의도와 다름, 재현 가능한 버그          | 미승인      |
| **경고** | 지금은 괜찮지만 곧 문제가 될 구조             | 조건부 승인 |
| **제안** | 취향 · 스타일 · 가독성                        | 조건부 승인 |

#### 승인 판정 기준

- **치명 · 결함이 0건 → 승인**
- **경고 · 제안만 있음 → 조건부 승인** (커밋해도 됨. 지적은 따로 기록)
- **치명 또는 결함이 1건 이상 → 미승인**

> **재현 시나리오를 쓸 수 없는 지적은 "치명"이나 "결함"이 될 수 없습니다.**
> "이럴 수도 있다"는 **경고**, "이게 더 낫다"는 **제안**입니다.
> 구체적인 입력과 잘못된 결과를 적을 수 있을 때만 결함으로 올리세요.
> **이 규칙이 무한 재수정 루프를 막습니다.**

### 4.5 당신의 지적은 반박될 수 있습니다

Claude는 당신의 지적을 **판정 대상**으로 다룹니다. 무조건 고치지 않습니다.

- 맞는 지적 → 고치고 보고
- **틀린 지적 → 코드 근거를 들어 반박하고 사용자에게 보고**
- 취향 문제 → 사용자에게 선택지로 제시

반박이 오면 감정 없이 재검토하세요. 당신이 맞으면 근거를 더 대고, 틀렸으면 철회하세요.
**철회는 실패가 아닙니다.** 틀린 지적을 고집해서 멀쩡한 코드를 고치게 만드는 것이
이 워크플로의 가장 큰 실패입니다.

### 4.6 라운드 상한

**한 변경당 검수는 최대 2라운드입니다.** 2라운드 후에도 남은 이견은 아래 형식으로
사용자에게 넘기고 **사용자가 결정**합니다.

| 쟁점 | Codex 입장 | Claude 입장 | 사용자 결정 |
| ---- | ---------- | ----------- | ----------- |

### 4.7 이 프로젝트에서 꼭 알아야 할 규칙

**이걸 모르면 틀린 지적을 하게 됩니다.**

#### 아이템 · 전투

- 새 공격 거동은 반드시 **공격 프로필(`PlayerAttackProfile`)의 속성**으로 만듭니다.
  씬·시스템 코드에서 **아이템 id로 분기하면 그것이 결함**입니다
- 씨앗 발사는 `Player.spawnSeedFan` **한 경로만** 씁니다. 별도 `Bullet.spawn` 지점을
  만들면 결함입니다
- **단일 아이템이 혼자서 초당 화력을 2배 넘게 올리면 안 됩니다.**
  특히 곱셈 배율(`damageMultiplier`)이 여러 개 겹치는 것을 주의해서 보세요

#### 구조

- 판단 규칙은 `systems/*Rules.ts`에 **순수 함수**로 두고 단위 테스트를 붙입니다.
  Phaser에 의존하면 테스트할 수 없습니다
- 엔티티가 스폰 정책 상수를 직접 읽으면 계층 위반입니다 (파라미터로 받아야 함)
- 랜덤은 `RandomSource`를 주입받아 테스트에서 재현 가능해야 합니다

#### 기존 동작 불변

- **스테이지 보스 4종과 중간보스 4종의 동작은 바꾸지 않습니다.**
  공용 기반(`BaseEnemy` 등)을 건드리는 변경이면 이들에게 영향이 가는지 확인하세요
- 방 재진입 시 상태 복원(보상·폭탄·상자·상점)은 **터질 때/주울 때 목록에서 지우는
  것**이 핵심입니다. 안 지우면 방에 들어올 때마다 되살아나 무한히 늘어납니다

#### Phaser 함정 (실제로 당한 것들)

- **물리 그룹은 자식을 추가하는 순간 바디에 그룹 기본값을 덮어씁니다.**
  감속·반발·속도 상한을 **생성자에 쓰면 조용히 0이 됩니다.**
  그룹 설정이나 `createCallback`으로 줘야 합니다
- **정적 바디는 `setScale`을 따라가지 않습니다.** 그림을 줄이면 충돌 범위를 직접
  지정해야 합니다 (안 하면 보이지 않는 벽처럼 느껴집니다)
- 히트스톱에 물리 월드 `pause`/`timeScale`을 쓰지 않습니다 (다른 타이머가 어긋남)
- 열린 문 통과는 물리 충돌이 아니라 **좌표를 가두는 계산**(`clampToRoomBounds`)이
  담당합니다. 문마다 경계를 덮어쓰지 말고 **누적**해야 합니다

#### 배경 지식

- 해상도 480×272, 16px 격자, 방 안쪽 416×208 (좌 32 · 상 32 시작), 벽 두께 16, 문간 폭 48
- 총 8층 (4스테이지 × 2층), 각 층 끝에 보스 (I층 중간보스, II층 스테이지 보스)
- 아이템 36종, 시너지 6종, 적 15종, 전투방 템플릿 12종
- 자세한 것은 [`docs/`](README.md) 폴더의 기능별 문서를 보세요

## 5. 검수 결과를 받은 Claude가 할 일

1. 지적을 **맞음 / 틀림 / 취향**으로 분류
2. 맞음 → 최소 범위로 수정 + **회귀 테스트 추가** (그 테스트가 수정 전 코드에서
   실패하는지 확인)
3. 틀림 → 코드 근거를 들어 반박문 작성
4. 취향 → 사용자에게 선택지로 제시
5. `npm run check` 재통과
6. **커밋하지 않고** 사용자에게 보고
