## 협업 방식

### 역할

| 누가       | 무엇                                                        |
| ---------- | ----------------------------------------------------------- |
| **사용자** | 방향 결정, 직접 플레이 테스트, "재미있는가" 판단, 커밋 실행 |
| **Claude** | 주 개발자. 구현 · 버그 수정 · 자동 테스트 · `npm run check` |
| **Codex**  | 2차 검수자. 고위험 변경의 diff만 판정 (2026-09-05 재개)     |

사용자는 코딩 초보이므로 **설명은 쉽게**, 다만 과한 비유와 원칙 번호 태그는 쓰지 않습니다.

### 검수 방식 (2026-09-05 확정)

**위험도에 따라 검수 깊이를 다르게 합니다.** 전부 검수하면 시간만 쓰고, 정작 v1.0을
막고 있는 4항목이 안 끝납니다.

| 위험도     | 무엇                                                                         | 검수                       |
| ---------- | ---------------------------------------------------------------------------- | -------------------------- |
| **저위험** | 수치 튜닝 · 색 · 단일 상수 · 데이터 1~2개 · 문서 · 도트 그림                 | 없음 → 바로 커밋           |
| **중위험** | 기존 시스템 안의 로직 변경 · 순수 함수 규칙 수정 · UI 표시 · 테스트 추가     | `/code-review`만           |
| **고위험** | 새 시스템 · 상태 기계 · 물리·충돌 · 여러 시스템 배선 · 저장·복원 · 입력 처리 | `/code-review` → **Codex** |

애매하면 한 단계 위로 올립니다. 검수는 **한 변경당 최대 2라운드**이고, 남은 이견은
사용자가 결정합니다. Codex의 지적은 **수정 대상이 아니라 판정 대상**입니다 — 틀린
지적은 근거를 들어 반박합니다.

전체 순서, Codex에게 건네는 안내글, 판정 형식과 승인 기준은
**[12. 검수 워크플로](12-review-workflow.md)** 에 있습니다.

Codex 시절 기준(회귀 위주, 기존 보스 동작 불변, 순수 함수 분리)은 그대로 이어 갑니다.

### 반드시 지킬 것

1. **명시적 요청 없이 커밋·푸시하지 않습니다.** 구현이 끝나면 `npm run check` 통과를
   확인하고 **커밋 없이 멈춰서 보고**합니다. 커밋 메시지는 요청하면 써 줍니다
2. **커밋되지 않은 변경을 임의로 삭제·되돌리지 않습니다.** 사용자의 작업일 수 있습니다
3. **습관적으로 동의하지 않습니다.** 결론 → 이유 → 선택지 → 사용자가 결정 순서로
   답하고, 사실·기술 판단·취향을 구분합니다. 사용자가 원하는 방향이라도 안전·버그·
   유지보수 문제는 미리 경고합니다
4. **구현 절차**: 기존 코드 확인 → 충돌·영향 설명 → 최소 범위 구현 → 검사 →
   커밋 없이 정지. 요청 범위를 임의로 넓히지 않습니다
5. **아이디어 스코프 4단계**: 기존 구조에 작게 얹으면 v1.0 / 새 대형 시스템은 v1.1 /
   기반 변경(조작·피해 모델)은 비용·위험 먼저 경고 / 애매하면 견적 먼저
6. **v1.0 체크리스트에 없는 것은 하지 않습니다.** 작업이 끝나면 "다음 뭐 할까요"
   대신 체크리스트의 다음 항목을 먼저 제시합니다. 벗어나려면 근거를 대고 합의합니다
7. 이 게임은 첫 작품이자 다음 게임을 위한 발판입니다. **아이작 모방은 의도된 학습
   방식**이므로 "독창성 부족"을 문제 삼지 않습니다
8. 검수·문서·커밋 메시지에 **비밀번호 평문, 해시 생성 과정, 비밀 입력 순서를 적지
   않습니다**

### 새 작업을 시작하기 전 확인 절차

1. `git status --short --branch`로 커밋되지 않은 변경을 확인
2. [`docs/00-status-overview.md`](00-status-overview.md)와 관련 기능 문서를 읽기
3. `git log --oneline -10`으로 문서 작성 이후의 최근 커밋 확인
4. 요청한 기능과 관련된 **실제 코드**를 읽고 문서가 여전히 맞는지 검증
5. 작업 후 `npm run check` 실행
6. 직접 플레이가 필요한 기능은 자동 검사와 별도로 브라우저에서 확인

**문서보다 실제 코드와 Git 기록이 우선입니다.**
